

"배치 지연 사태"
신규로 수정된 배치가 기존보다 2배 이상 지연되는 일이 생기고야 말았다.
어느 구간에서 지연이 발생했는지 확인하기 위해 실행 중인 플랜을 살펴보았다.

"플랜의 한계"
사실 플랜을 통해 실행 중인 SQL이 어느 지점에서 막혀 있는지, 지연의 정확한 원인이 무엇인지 밝혀내는 방법은 없다.
그저 대량 테이블이 Table Full Scan 발생하는지 확인하는것 뿐이다.

나중에 쿼리와 바인드 변수를 받아서 실행 계획을 봤을때 가장 많은 cost를 사용하는 구간이 어딘지를 통해서 알아내는,
그저 사후 튜닝을 진행하는 일이 유일하다.

"wait event를 통한 병목 원인 확인" 
다행히 모니터링 툴에서 돌고 있는 쿼리의 wait event까지는 파악할 수 있다. 물론 CPU가 95~99% 정도 차지하겠지만 간혹 이상한 경우가 발견될 때가 있다.

이번에 발견했던 것은 lru cache 관련 wait였다. 특히 개발팀과 함께 확인했을 때 문제로 의심 삼았던 NL Join과 관련이 깊을 것으로 예상을 하며 lru cache에 대해 깊게 살펴보았다.

"오라클 내부 메모리 중 버퍼 캐시의 구조"
오라클은 SGA라는 이름의 인스턴스 메모리 영역을 가진다.
Shared Global Area라는 뜻이다. 공유를 위한 공간으로 메타데이터 혹은 캐시를 포함한 데이터를 관장한다.

그 중에서 Data Buffer Cache라는 영역이 있다. 데이터의 일부를 메모리상에 캐싱해둠으로써 조회 성능을 높이기 위함이다.

난 위 단계까지만 알고 있었다. 하지만 이번에 발견되었던 wait event를 정확하게 알기 위해서는 좀 더 상세한 구조와 동작 방식을 알아야만 했다.

"단순히 블록을 가져다 저장해놓는 것이 아님"

Data Buffer Cache의 메인 메모리 주소를 버퍼라고 하며 디스크 파일에 있는 데이터 블록은 버퍼에 메모리 복사를 한 후, 조회나 수정을 하는 것이다.
버퍼에 대한 메타데이터는 버퍼 헤더에 저장한다. 그리고 버퍼는 LRU list로 관리된다.

참고로 Update 쿼리가 발생해서 데이터 블록의 변경사항에 대해선 redo log buffer에 저장한다. commit이 발생하게 되면 redo log buffer를 online redo log에 기록한다.
그리고 DBWR이 데이터 블록을 데이터 파일에 기록한다.

Database Smart Flash Cache를 사용하도록 설정하면 buffer cache의 일부를 flash cache로 배치시킬 수 있다.
하나 이상의 flash device에 저장하게 되는데 데이터베이스는 magnetic disk에서 읽는 대신 flash memory에 buffer를 캐싱하여 성능 향상을 꾀할 수 있다.
DB_FLASH_CACHE_FILE 파라미터를 이용해서 여러 flash device를 구성하여 buffer를 device에 균등하게 분산 및 트래킹할 수 있다.

버퍼 상태에는 크게 세 가지가 있다.
- Unused : 한 번도 사용하지 않고 현재 사용중이지도 않은 버퍼
- Clean : 이전에 사용된 적이 있으나 현재 시점에는 MVCC에 의해 읽기 일관성이 보장된 상태. 체크포인트를 수행할 필요가 없으며 고정하고 재사용할 수 있다.
- Dirty : 디스크에 기록되지 않은 수정된 데이터가 있을 경우. 블록을 재사용하기 전에 체크포인트를 수행해야 한다.

일관성을 보장하기 위해 체크포인트를 수행하는 것이며 그렇기 때문에 User 세션은 고정(pinned) 또는 해제(free, unpinned) 액세스 모드로 버퍼에 접근하게 된다.
여러 세션이 동시에 고정된 버퍼를 수정할 수 없다.

버퍼를 검색할 때는 current 모드와 consistent 모드가 있다.
db block get이라고 불리는 current 모드는 버퍼 캐시에서 가장 최신화된 블록을 가져올 때 사용한다.
update를 수행하기 위해서이다.

반면 consistent 모드는 undo에서 특정 MVCC 버전에 해당되는 블록을 가져온다.
특정 세션에서 커밋되지 않은 업데이트가 발생할 경우 데이터 일관성을 보장하기 위해 변경 전 블록이 생성되는데 그걸 검색한다는 뜻이다.

참고로 MVCC 버전 처리는 블록 헤더에 저장되어 있는 SCN 번호를 이용해서 색출해낸다.

기본값으로 사용되는 LRU-based, block-level replacement algorithm 알고리즘은 dirty 버퍼와 non-dirty 버퍼에 대한 포인터가 포함된 LRU(Least Recently Used) 리스트를 사용한다.
LRU 리스트에는 Hot End와 Cold End가 있고 cold 버퍼는 최근에 사용되지 않은 버퍼이며 hot 버퍼는 자주 액세스되며 최근에 사용된 버퍼를 의미한다.
수정이 발생해 dirty 상태가 된 버퍼들을 따로 모아두는 곳은 LRUW 리스트이다. DBWR(Database Writer) 프로세스가 이 리스트를 스캔하여 디스크에 일괄 기록하는 것이다.

개념적으로는 하나의 LRU만 존재하지만, 데이터 동시성을 위해 데이터베이스는 실제로 여러 개의 LRU 리스트를 사용한다.
LRU 리스트는 실제 버퍼가 저장되는 것이 아닌, 상태와 위치와 같은 메타데이터를 가지고 있는 '버퍼 헤더'가 저장된다는 사실에 유의해야 한다.

+-----------------------------------------------------------------------------------------+
|                             TOUCH-COUNT BASED LRU MAIN LIST                             |
+-----------------------------------------------------------------------------------------+

 MRU End (Most Recently Used)                                 LRU End (Least Recently Used)
 +-------------------------------------+ +------------------------------------------------+
 |             HOT REGION              | |                  COLD REGION                   |
 |    (Frequently Accessed Blocks)     | |         (New Entrants & Victim Blocks)         |
 +------------------+------------------+ +-----------------------+------------------------+
 |     Hot Head     |     Hot Tail     | |    Cold Head (Mid)    |       Cold Tail        |
 +------------------+------------------+ +-----------------------+------------------------+
          ^                                          |                      |
          | (Promoted when TCH >= 2)                 | (TCH <= 1)           |
          +------------------------------------------+                      v
                                                                   [Free Buffer Victim]


LRU, LRUW 리스트를 Working Set이라고 불리며 "메모리 공간에 대한 수명 관리"에 대한 목적이 있다고 하면 해시 체인은 "빠른 데이터 탐색"이라는데 목적이 있다.
해시 체인은 블록 주소(DBA)를 해싱하여 데이터가 메모리의 어디에 있는지 빠르게 찾아내는 역할을 하는데 
만일 쿼리가 데이터를 찾을 때는 LRU 리스트를 처음부터 뒤지지 않고 이 해시 체인을 통해 버퍼 헤더에 즉시 접근한다.

"SQL 유형별 유기적 동작 흐름"
위의 개념들은 실제 쿼리가 실행될 때 해시 체인(위치 탐색)과 Working Set(공간 관리)을 거치며 다음과 같은 순서로 진행이 이뤄지게 된다.

조회 쿼리 (SELECT - Consistent 모드)
- 위치 탐색: 블록 주소를 해싱하여 해시 체인에서 버퍼 헤더를 찾는다.
- 공간 확보: 캐시에 블록이 없다면, LRU 리스트의 Cold End에서 프리 버퍼를 확보해 디스크 데이터를 적재한다.
- CR 복제: 원본이 Dirty 상태라면, Consistent 모드로 Undo를 참조해 과거 시점의 읽기 전용 복제본을 LRU 리스트에 생성한다.

수정 쿼리 (UPDATE - Current 모드)
- 최신 탐색: 해시 체인을 통해 가장 최신 상태인 원본 버퍼 헤더를 찾는다.
- 데이터 변경: 락(Pin)을 걸고 데이터를 수정하여 버퍼를 Dirty 상태로 만든다.
- 쓰기 대기: 수정이 완료된 버퍼 헤더는 LRU 리스트에서 빠져나와, 디스크 기록을 위해 Working Set의 LRUW 리스트로 이동한다.

"Touch Count"
캐싱에 성공할 경우, 버퍼 헤더에 있는 접근 횟수를 +1한다. 
단, 악성 쿼리 발생으로 쏠림 방지를 위해 _db_aging_touch_time 히든 파라미터를 이용해 3초에 한 번씩 올린다.
터치 카운트가 올라갔다고 해서 버퍼가 바로 Hot 영역으로 이동하지는 않는다.
LRU 리스트에서의 이동은 cost가 높기 때문에 조회할 때마다 발생시키에 부담이 있기 때문이다.
대신 리스트에 없는 블록 조회로 인해 프리 버퍼를 할당받는 경우, LRU 리스트를 스캔할 때 수행되며 이 때 'free buffer waits' 이벤트가 발생된다.

"Hot과 Cold"
디스크에서 새로 프리버퍼에 할당 받을 경우에 Cold Trail에만 배치된다.
이후 Touch count가 2 이상이 될 경우, Hot 영역으로 진입되는데 이 때 Touch count는 0으로 초기화된다. 
지나친 상주에 따른 조회 성능 저하를 방지하기 위함이다.

"write complete waits"
LRU 리스트의 구조 변경이 발생할 때 Touch count에 따라 Hot과 Cold 영역에 있던 버퍼 헤더들간의 교체혈전이 Cold 영역의 방출이 이뤄질 수 있다.
근데 하필 쫓겨날 버퍼가 dirty 상태일 경우에는 쓰기 작업이 완료될 때까지 대기하게 되는데 이 때 발생하는 wait event가 write complete waits이다.

"latch: cache buffers lru chain"
앞서 언급했던 내용들에서 아래와 같은 이유로 LRU 리스트 구조 변경을 위한 '스캔'이 이뤄질 때마다 pin이 걸리면서 wait event가 발생했던 것이다.
'프리 버퍼 할당을 위한 LRU 스캔', 'Hot과 Cold의 교체혈전', 'dirty 버퍼의 LRUW 이동','DBWR 디스크 쓰기를 위한 LRUW 스캔 및 쓰기 완료 후 LRU 반납'
즉, 대량 데이터 처리 작업에 의한 캐시 메모리 할당의 여파였던 것이다.

"latch: cache buffers chains"
위 이벤트는 LRU 리스트가 아닌 해시 체인에서 발생하는데 구조를 먼저 서술하겠다.
일반적인 해시 테이블과 유사하게 bucket, entry로 구성된다.

[ Hash Function ] : Inputs a Data Block Address (DBA) and returns a bucket number between 0 and N.

[ Hash Bucket Array ]       [ Hash Chain (Doubly Linked List of Buffer Headers) ]
                                 (Entry 1)              (Entry 2)
┌─────────────┐             ┌─────────────────┐    ┌─────────────────┐
│ Bucket #0   │ ── Pointer ─▶│ Buffer Header A  ◀▶ │ Buffer Header F 
├─────────────┤             └─────────────────┘    └─────────────────┘
│ Bucket #1   │ ── (Empty - No data hashed to this bucket yet)
├─────────────┤             ┌─────────────────┐
│ Bucket #2   │ ── Pointer ─▶│ Buffer Header B 
├─────────────┤             └─────────────────┘
│ ...         │ 
├─────────────┤             ┌─────────────────┐    ┌─────────────────┐
│ Bucket #100 │ ── Pointer ─▶│ Buffer Header C  ◀▶ │ Buffer Header D 
└─────────────┘             └─────────────────┘    └─────────────────┘

해시 체인에 새로 할당되는 경우, LRU 리스트에 프리 버퍼를 할당받고 난 뒤에 블록 헤더에 있는 DBA 주소를 해시함수를 통해 나온 값에 따라 entry에 배정된다.
반대로 이미 해시 체인에 원하는 블록에 대한 버퍼 헤더가 버킷에 존재하는 경우에는 LRU 리스트 스캔은 스킵한다.
바로 이 버킷에 할당 받거나 스캔할 때 위 wait event가 발생하는 것이다.
다만 유의할 점은 버킷 단위로 잠금을 수행하지 않고 버킷을 관리하는 래치 단위로 잠금이 이뤄진다는 것이다. (래치와 버킷은 1:N 관계)
래치가 관리하고 있는 버킷에 여러 세션이 동시에 접근하는 '핫 블록'현상이 발생할 경우에 상황은 세션 수만큼 악화된다.

이처럼 문제는 래치의 수이다.
버킷 하나당 래치가 1:1로 관리하는 구조였으면 wait event가 덜 발생했을 것이다.
하지만 래치 또한 메모리를 차지하고 있기 때문에 공간 절약을 위해 버킷의 수보다 적게 할당된다.
데이터를 저장하는 버킷이 중요하지 자물쇠용 래치는 많이 둘 필요가 없기 때문이다.

래치의 수는 _db_block_hash_latches 히든 파라미터로 확인이 가능한데 cpu core 수에 따라 값이 정해진다.
(_db_block_hash_buckets의 수는 전체 메모리 관리 변수인 memory_target에 따라 결정)
따라서 스케일 업을 진행하면 어느 정도 해소가 될 수 있겠지만 하나의 버킷에 쏠리는 경우에는 답도 없다.

이 경우에는 PCT Free를 높게 줘버려서 디스크 공간 낭비는 있겠지만 블록 소산을 유도하는 방법이 있다.
또는 해시 파티셔닝을 사용해서 별도 세그먼트에 배정시키는 방법이 있는데 이 경우에는 범위 조회에 대한 성능이 저하된다.
또한 여러 블록으로 쪼개짐에 따른 LRU 캐싱 성능도 같이 떨어질 수 밖에 없다. 
해결하려던 시도가 다시 원점 유발로 돌아오는 셈. 리버스 인덱스 적용도 마찬가지.

"결국 제일 중요한 것은 buffer gets"
애당초 디스크로부터 가져올 block의 수가 적으면 이런 문제들이 근본적으로 사라진다.
아니면 Table Full Scan을 이용해서 Direct Path I/O를 수행하면 메모리에 복사하고 연산하는 작업이 줄게 된다.
Hash Join을 사용해서 SGA와 같은 공유 공간이 아닌 PGA처럼 별도 세션 공간에서 수행하는 방법도 안전성을 높일 수 있다.
가장 최적화된 방안은 선행 테이블에 대해서 index range scan을 1회해서 빠르게 해시 테이블을 만든 후, 후행 테이블은 PGA에서 반복 연산 수행일 것이다.
